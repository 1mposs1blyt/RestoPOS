# Кухня: станции, экраны и печать марок

Как заказ попадает к тому, кто его готовит. Документ покрывает случай, ради
которого всё это устроено именно так: **на кухне может быть и монитор, и принтер
одновременно**, и они обязаны показывать одно и то же.

Разграничение доступа — в `docs/access.md`, архитектурные инварианты — в `CLAUDE.md`.

## 1. Модель

```
Станция приготовления            «Горячий цех» · «Бар» · «Пицца»
  └── выводы (0..N)
        ├── экран   → KDS-терминал
        └── принтер → ESC/POS по TCP
```

Ключевое решение: **экран и принтер — не два механизма, а две точки вывода одной
станции**. Отправка позиций на станцию — одно событие; сколько у станции выводов,
столько получателей у одного и того же тикета.

Развести их на «KDS» и «печать» — самая дорогая ошибка в этом месте. Логика
раздвоится, и рано или поздно напечатается то, чего нет на экране: два пути
кода расходятся при первой же правке.

Отсюда следствия, которые не надо программировать отдельно:

| Конфигурация станции | Что получается |
|---|---|
| только экран | обычный KDS |
| только принтер | кухня «по бумаге», типовая для тарифа без модуля `kds` |
| экран + принтер | дублирование — то, ради чего документ |
| ничего | позиции уезжают, но сообщить о них некому (экран настройки предупреждает) |

## 2. Пять правил

1. **Маршрутизация по позиции, а не по заказу.** Станцию задаёт блюдо
   (`menu_items.prep_station_id`): горячее уезжает на кухню, эспрессо — на бар.
   Один заказ порождает столько тикетов, на сколько станций разъехались его
   позиции. Бар не должен видеть стейки.
2. **Печать идёт через очередь.** Не прямой вызов принтера при отправке заказа:
   принтер не должен блокировать кухню, упавшее задание обязано быть видимым
   и повторяемым.
3. **Бумага не влияет на статус заказа.** Источник истины — заказ (инвариант №3),
   а не марка. Не напечаталось — заказ всё равно ушёл, тикет висит на экране,
   задание горит красным. Гость не должен ждать, пока в принтере кончится лента.
4. **Повтор явный и помеченный.** Копия печатается с шапкой «*** КОПИЯ ***»
   и требует права `print.reprint`. Молчаливый дубль марки — это второе
   приготовленное блюдо.
5. **Печатаем только то, что ушло именно сейчас.** Состав марки считается
   до перевода позиций из `new`: повторная отправка заказа не перепечатывает
   то, что повар уже готовит.

## 3. Что происходит при отправке заказа

```
официант жмёт «Отправить на кухню»
   ↓
позиции в статусе `new` группируются по станциям
   ↓
для каждой станции:
   ├── позиции переводятся в `cooking`   (у станции есть экран)
   │   либо сразу в `ready`              (экрана нет — см. §4)
   └── на каждый включённый принтер станции ставится задание печати
   ↓
исполнитель очереди берёт задания по одному
   ↓
`printed` либо `failed` с текстом ошибки
```

Отправка и постановка марок в очередь — **одна операция** (`fireOrder`), а не два
вызова подряд в каждом экране. Разъехавшись, они дают повару на бумаге не то,
что у него на экране.

Задания исполняются строго по одному: у принтера один буфер, и две марки,
пущенные параллельно, приезжают вперемешку.

## 4. Станция без экрана

Тикеты живут от статусов позиций, а двигает статусы KDS. У станции с одним
принтером двигать их некому — и тикеты копились бы вечно, засоряя в том числе
очередь выдачи на прилавке, которая строится из тех же данных.

Поэтому станция без включённого экрана считается работающей «по бумаге»:
позиции становятся `ready` сразу при отправке. Марка напечатана — считаем, что
повар её видит.

Отдаёт готовое человек, а не кухня: право `order.item.serve` (официант, кассир,
менеджер), кнопка «Отдано» в чеке и «Выдал» в очереди прилавка. Это не то же
самое, что `kitchen.item.status`: «готово» отмечает кухня, «отдано» — тот, кто
донёс до стола.

Признак «есть экран» **не хранится флагом** — он выводится из выводов станции.
Иначе один факт лежал бы в двух местах и разъезжался при перенастройке.

## 5. Марка

Денег на кухонной марке нет: повару они не нужны, а лишняя строка — это лишняя
секунда на чтение в час пик.

```
        *** КОПИЯ ***          ← только у повторной печати
           Горячий цех
            Стол 12            ← двойная высота: читается от плиты
             19:42
--------------------------------
2 x Фо Бо
1 x Стейк Рибай
```

Кухонная марка и чек гостю — разные вещи: марка печатается при отправке
на кухню, пречек и фискальный чек — при расчёте, на другом принтере
и по другому праву.

## 6. Печать: где что живёт

Граница между слоями: **фронт решает, ЧТО печатать, Rust — КАК**.

- `src/state/printing.tsx` — очередь заданий, состав марки, повторы.
- `src/lib/printer.ts` — мост в Tauri; вне приложения (`pnpm dev` в браузере)
  честно возвращает ошибку, а не молчаливый успех.
- `src-tauri/src/printing.rs` — кодировка CP866, ESC/POS-команды, сырой TCP
  с таймаутом.

Кодировка — причина, по которой печать не сделать во фронте: принтер понимает
кириллицу только в своей кодовой странице, а в браузере нет ни кодировщика
под CP866, ни сырого сокета. Таблица CP866 написана вручную (три диапазона
подряд) — ради них не стоит тащить зависимость в каждую сборку.

Сокет блокирующий и уводится с потока рантайма: недоступный принтер иначе
подвесил бы интерфейс кассы на весь таймаут.

## 7. Контракт бэкенда

### Дельта схемы

```sql
-- Станции приготовления заведения. Пришли на смену перечислению
-- 'kitchen' | 'bar': у ресторана бывают холодный и горячий цеха, пицца, суши,
-- а менять перечисление под клиента означает пересборку ради данных.
CREATE TABLE IF NOT EXISTS prep_stations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    venue_id UUID REFERENCES venues(id),
    name TEXT NOT NULL,
    sort_order INT NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_prep_stations_venue ON prep_stations(venue_id);

-- Точки вывода станции. Экран и принтер в одной таблице намеренно:
-- дублирование — это две строки, а не отдельный механизм.
CREATE TABLE IF NOT EXISTS station_outputs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    station_id UUID REFERENCES prep_stations(id) ON DELETE CASCADE,
    kind TEXT NOT NULL,                 -- 'screen' | 'printer'
    name TEXT NOT NULL,
    host TEXT,                          -- только для 'printer'
    port INT,                           -- ESC/POS RAW, обычно 9100
    is_enabled BOOLEAN NOT NULL DEFAULT TRUE
);
CREATE INDEX IF NOT EXISTS idx_station_outputs_station ON station_outputs(station_id);

-- Очередь печати. Исполнитель забирает задания и проставляет статус.
CREATE TABLE IF NOT EXISTS print_jobs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    venue_id UUID REFERENCES venues(id),
    output_id UUID REFERENCES station_outputs(id),
    station_id UUID REFERENCES prep_stations(id),
    order_id UUID REFERENCES orders(id),
    item_ids UUID[] NOT NULL,
    status TEXT NOT NULL DEFAULT 'queued', -- 'queued'|'printing'|'printed'|'failed'
    is_reprint BOOLEAN NOT NULL DEFAULT FALSE,
    attempts INT NOT NULL DEFAULT 0,
    error TEXT,
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_print_jobs_pending
    ON print_jobs(venue_id, status, created_at);

-- Блюдо знает свою станцию. Раньше было prep_station TEXT.
ALTER TABLE menu_items DROP COLUMN IF EXISTS prep_station;
ALTER TABLE menu_items ADD COLUMN IF NOT EXISTS prep_station_id UUID
    REFERENCES prep_stations(id);

-- Кухонный монитор обслуживает одну станцию.
ALTER TABLE terminals ADD COLUMN IF NOT EXISTS prep_station_id UUID
    REFERENCES prep_stations(id);
```

### Эндпоинты

- `GET /venues/:id/stations` — станции с выводами. Нужен и кассе (решить,
  что считать готовым сразу), и KDS, и экрану настройки.
- `POST/PATCH/DELETE /stations` и `/stations/:id/outputs` — `requirePermission('station.manage')`.
- `POST /orders/:id/fire` — отправка на кухню. **Здесь же** создаются `print_jobs`
  в одной транзакции с переводом позиций: заказ, ушедший без марок, — это блюдо,
  которое никто не готовит.
- `POST /print-jobs/:id/reprint` — `requirePermission('print.reprint')`.
- `GET /print-jobs?status=failed` — для алерта менеджеру.

Событие `print_job.failed` в комнату `pos` — по инварианту №3 без полезной
нагрузки, только сигнал перезапросить.

### Кто физически печатает

Два варианта, модель очереди для обоих одинакова:

- **Сетевой принтер** — печатает сервер. Предпочтительно: не зависит от того,
  включена ли касса, и переживает её перезагрузку.
- **USB-принтер в кассе** — задание забирает терминал и печатает через Tauri
  (`print_ticket`), сервер только держит очередь.

Сейчас реализован второй путь целиком на клиенте, потому что бэкенда ещё нет.
Когда появится сервер, `state/printing.tsx` меняет источник заданий с localStorage
на API, а `lib/printer.ts` и Rust остаются как есть.

## 8. Ограничения текущей реализации

- Очередь живёт в localStorage терминала: другой терминал её не видит,
  повторная печать с кассы у бара недоступна.
- Ретрая по таймеру нет — упавшее задание повторяет человек кнопкой.
- Станции настраиваются локально и на терминале; на проде это данные заведения.
- Печать проверена юнит- и интеграционными тестами на Rust (включая передачу
  в реальный сокет), но **не на живом ESC/POS-принтере** — железа под рукой
  не было. Кодовая страница `17` (CP866) верна для Epson и большинства клонов;
  если попадётся принтер с другой таблицей, менять одну константу
  `CODEPAGE_CP866` в `printing.rs`.
