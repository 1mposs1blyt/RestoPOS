# MVP для фастфуда: прилавок с одной кассой

Документ фиксирует объём первой версии для заведений формата «шаурмечная»:
одно заведение, один терминал, один человек за прилавком. Он не отменяет
`docs/plan.md` и `docs/access.md`, а сужает их до того, что нужно продать
первому клиенту, и перечисляет то, чего для этого не хватает на узле.

Целевая конфигурация — «шаурмечная навынос» из `docs/access.md` §2:

```
organization: тариф Start
venue:        service_mode = 'counter'
terminals:    1 × pos
staff:        владелец (manager) + 1–2 × cashier
```

Всё, что ниже, обязано следовать из данных этой конфигурации. Условий вида
`if (заведение — фастфуд)` в коде быть не должно: второй формат заведения
включается сменой `service_mode` и тарифа, а не второй сборкой.

---

## 1. Что входит и что не входит

**Входит:** вход по PIN, продажа с модификаторами, оплата наличными и картой,
фискальный чек, возврат по чеку, кассовая смена с X- и Z-отчётом, внесение,
изъятие и инкассация, стоп-лист, сервисный экран терминала, веб-админка
(меню, сотрудники, настройки, четыре отчёта).

**Не входит:** зал и схема столов, официанты и их заказы, деление блюда между
гостями, кухонный экран, станции и печать марок, склад и техкарты, доставка,
лояльность, ЕГАИС, мультиточка, облако.

Исключённое вырезается **данными и тарифом**, а не удалением кода: `kds`
и `warehouse` не оплачены тарифом Start, терминала `kds` в заведении нет,
`service_mode = 'counter'` убирает зал. Код зала и кухни остаётся в схеме
и в узле нетронутым.

## 2. Экраны кассы

Таблицы названы по канонической схеме `apps/backend/server/Data/schema.sql`.

### 2.1 Вход по PIN

- **Читает:** `staff`, `terminals`, `venues`, тариф организации.
- **Пишет:** —
- **Эндпоинты:** `POST /auth/pin`, `GET /session/bootstrap`, `POST /auth/override`.
- **Состояние:** есть на узле.

Ответ включает готовый список прав. Фронт права не вычисляет. Отказы
различаются по коду: `invalid_pin`, `staff_not_in_venue`, `no_screens_for_role`.

### 2.2 Продажа (главный экран)

- **Читает:** `menu_categories`, `menu_items`, `modifiers`, `stop_list`,
  `orders` (активные), `order_items`, `order_item_modifiers`.
- **Пишет:** `orders`, `order_items`, `order_item_modifiers`.
- **Эндпоинты:** `GET /api/v1/venues/{id}/menu` (есть), `POST /orders`,
  `POST /orders/:id/items`, `PATCH /order-items/:id`,
  `POST /order-items/:id/void` (нет).

Позиция с модификаторами открывает окно выбора. Цена позиции пишется
в `order_items.price` снимком на момент добавления. Цена модификатора должна
писаться снимком тоже — см. §5.3.

На прилавке заказ создаётся с `table_id = NULL`, гостя зовут по
`orders.number`.

### 2.3 Оплата

- **Читает:** `payment_types`, `discount_types`, текущий заказ.
- **Пишет:** `payments`, `order_discounts`, `orders.status = 'paid'`,
  `orders.cash_shift_number`, `orders.receipt_number`.
- **Эндпоинты:** `POST /orders/:id/pay` (нет).
- **Железо:** эквайринг и ККТ через Tauri, код есть в `src-tauri`.

Порядок операций неизменен: **эквайринг → фискальный чек → заказ оплачен**.
У операции три исхода, а не два: успех, отказ и неизвестный результат.
Последний обрабатывается отдельной веткой с компенсацией.

Оплата — список строк, а не один тип: наличные плюс карта в одном чеке
допустимы. `payments` иммутабельны и только добавляются.

### 2.4 Возврат по чеку

- **Читает:** `orders`, `payments` закрытой смены.
- **Пишет:** `payments` со ссылкой `refund_of`.
- **Эндпоинты:** `GET /orders?paid&period`, `POST /payments/:id/refund` (нет).

Повторный возврат по той же строке невозможен. Возврат деньгами на карту идёт
через эквайринг, затем печатается чек возврата прихода.

### 2.5 Кассовая смена

- **Читает:** `cash_shifts`, `cash_operations`, `payments` текущей смены.
- **Пишет:** `cash_shifts`, `cash_operations`, `shifts`, `staff_shifts`.
- **Эндпоинты:** `POST /shifts/open`, `POST /shifts/close`,
  `POST /cash-operations`, `GET /shifts/current/x-report` (нет).

Ответ на открытие смены включает **блок номеров заказов** для терминала
(`docs/autonomy.md` §6). При одном терминале блок не обязателен технически,
но контракт должен быть один: второй терминал не должен менять протокол.

X-отчёт считается узлом, а не фронтом: это тот же запрос, что и Z-отчёт,
только без гашения.

### 2.6 Стоп-лист

- **Читает / пишет:** `stop_list`.
- **Эндпоинты:** `GET /stop-list`, `PUT /stop-list/:menuItemId`,
  `DELETE /stop-list/:menuItemId` (нет).
- **Событие:** `stoplist.changed`.

Ставится кассиром прямо с экрана продажи, в одно нажатие. Позиция в стоп-листе
не исчезает из меню, а гасится: кассир должен видеть, что она существует.

### 2.7 Сервисный экран

- **Читает / пишет:** `terminals` (тип устройства, адрес ККТ, принтер чеков).
- **Эндпоинты:** `GET /terminals/:id`, `PATCH /terminals/:id` (нет).
- **Доступ:** роль `support`, право `terminal.service`, без доступа к деньгам
  и заказам.

## 3. Бек (веб-админка)

Отдельное React-приложение, которое узел раздаёт статикой. Открывается
в браузере на кассовом компьютере или с телефона владельца в локальной сети.
Когда появится облако, то же приложение будет раздаваться оттуда —
поэтому оно с самого начала живёт в `apps/backoffice`, а не разделом внутри
кассы.

| Раздел                            | Таблицы                                                                  | Операции                                                                                             |
| --------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Меню                                | `menu_categories`, `menu_items`, `modifiers`                              | CRUD, порядок сортировки                                                                    |
| Стоп-лист                       | `stop_list`                                                                   | снять, посмотреть                                                                             |
| Сотрудники                    | `staff`                                                                       | CRUD, смена PIN, роль                                                                               |
| Типы оплаты                   | `payment_types`                                                               | CRUD                                                                                                         |
| Скидки                            | `discount_types`                                                              | CRUD, флаг подтверждения                                                                    |
| Оборудование                | `terminals`                                                                   | ККТ, принтер чеков                                                                            |
| Фискальные реквизиты | `venues`, `menu_items`                                                      | СНО, ставка НДС, признак предмета расчёта (см. §5.1)                    |
| Отчёты                            | `orders`, `payments`, `order_items`, `cash_shifts`, `cash_operations` | выручка за период, по позициям, по кассирам, по типам оплаты |
| Журнал                            | `audit_log`                                                                   | просмотр опасных операций                                                             |

Права на разделы — те же коды из `contracts/contract.json`, что и на кассе.
Отдельной матрицы для Бека не заводим.

## 4. Чего не хватает на узле

Сейчас узел отдаёт сессию, столы, занятость и меню (`CLAUDE.md`). Для MVP
не хватает перечисленного ниже. Порядок — это и есть порядок работ.

### 4.1 Касса, чтение и запись оперативных данных

| Метод                              | Назначение                                                                |
| --------------------------------------- | ----------------------------------------------------------------------------------- |
| `POST /orders`                        | открыть заказ,`{ clientId, tableId: null }`                           |
| `POST /orders/:id/items`              | добавить позицию с модификаторами                     |
| `PATCH /order-items/:id`              | количество до отправки                                          |
| `POST /order-items/:id/void`          | сторно, побиваемое право                                       |
| `POST /orders/:id/pay`                | оплата списком строк                                              |
| `POST /orders/:id/cancel`             | отмена заказа                                                           |
| `POST /payments/:id/refund`           | возврат по строке платежа                                     |
| `POST /shifts/open`                   | открытие смены, ответ с блоком номеров              |
| `POST /shifts/close`                  | закрытие с гашением                                                |
| `POST /cash-operations`               | внесение, изъятие, инкассация, разменный фонд |
| `GET /shifts/current/x-report`        | X-отчёт                                                                        |
| `GET /stop-list`, `PUT`, `DELETE` | стоп-лист                                                                   |

### 4.2 Бек, запись справочников

Этих эндпоинтов нет в `docs/plan.md` §4 вообще: там справочники только
читаются, потому что предполагалось, что их хозяин — облако. **Пока облака
нет, хозяин справочников — узел**, и Беку нужна запись.

| Ресурс                  | Методы                                             |
| ----------------------------- | -------------------------------------------------------- |
| `/menu/categories`          | `POST`, `PATCH`, `DELETE`                          |
| `/menu/items`               | `POST`, `PATCH`, `DELETE`                          |
| `/menu/items/:id/modifiers` | `POST`, `PATCH`, `DELETE`                          |
| `/staff`                    | `GET`, `POST`, `PATCH`, `DELETE`, смена PIN |
| `/payment-types`            | `GET`, `POST`, `PATCH`, `DELETE`                 |
| `/discount-types`           | `GET`, `POST`, `PATCH`, `DELETE`                 |
| `/terminals/:id`            | `GET`, `PATCH`                                       |
| `/venues/:id`               | `GET`, `PATCH`                                       |
| `/reports/*`                | четыре отчёта из §3                       |
| `/audit-log`                | просмотр с фильтрами                   |

Удаление справочников — только `deleted = TRUE`. Физически удалять нельзя:
на строку ссылаются закрытые чеки.

### 4.3 Realtime

Транспорт нужно зафиксировать до реализации: `packages/api-client` написан под
**socket.io**, а `docs/plan.md` §3 рекомендует узлу **SignalR**, и эти два
протокола несовместимы. Решение записать рядом с `eventTopics`
в `contracts/contract.json`.

Для MVP достаточно событий `order.updated`, `stoplist.changed`,
`shift.changed`. Подписчик пока один, но контракт должен быть тем же, что
и для нескольких терминалов.

## 5. Пробелы схемы, которые закрываются до первой установки

### 5.1 Фискальные реквизиты

В `venues` нет системы налогообложения, в `menu_items` — ставки НДС и признака
предмета расчёта. Без них чек по 54-ФЗ не собрать, а это не опциональная
функция, а условие продажи. Нужны колонки (или явные ключи в `attributes`
с описанием в `custom_field_defs`), плюс поля в Беке.

### 5.2 Группы модификаторов

`modifiers` сейчас — плоский список у позиции: имя и `price_delta`. Фастфуду
этого мало: нужны группы с правилами «выбрать ровно один» (размер, острота)
и «выбрать сколько угодно» (добавки). Без групп правила придётся зашивать
в интерфейс кассы, и они разъедутся с Беком.

Минимум: таблица `modifier_groups` (`menu_item_id`, `name`, `min_select`,
`max_select`, `sort_order`) и ссылка `modifiers.group_id`.

### 5.3 Цена модификатора снимком

`order_item_modifiers` хранит только пару идентификаторов. Цена берётся
из `modifiers.price_delta`, то есть из справочника. Подорожание добавки
изменит сумму **уже закрытых** чеков и разойдётся с Z-отчётом. Нужны
`price_delta` снимком и `quantity` в самой `order_item_modifiers` — по той же
логике, по которой `order_items.price` уже снимок, а `payments.label`
продублирован из справочника.

### 5.4 Сортировка и активность позиций меню

Для плиточного экрана нужны `menu_items.sort_order` и признак активности
(либо `deleted`, либо отдельный `is_active`, если позиция скрывается временно).
У категорий `sort_order` уже есть.

### 5.5 Миграции

Таблица `schema_migrations` есть, инструмента нет, `DatabaseInitializer`
неоткуда вызвать. Завести до первой боевой установки: после неё менять схему
руками по живой базе клиента будет нельзя.

## 6. Признаки готовности

1. Кассир входит по PIN, открывает смену, продаёт шаурму с модификаторами,
   принимает наличные и карту, печатает фискальный чек.
2. Владелец через Бек добавляет позицию в меню, и она появляется на кассе
   без перезапуска приложения.
3. Смена закрывается с Z-отчётом, суммы сходятся с `payments`
   и `cash_operations`.
4. Возврат по вчерашнему чеку проходит и повторно не проводится.
5. Заведение работает при выдернутом интернет-кабеле — всё, кроме оплаты
   картой; касса говорит об этом кассиру явно.
6. Переключение `service_mode` на `tables` и тарифа на Standard возвращает
   зал и кухню без правок кода.
