# Автономность и синхронизация

Заведение обязано работать при обрыве интернета. Документ описывает топологию,
которая это обеспечивает, и правила синхронизации между контурами.

Разграничение доступа — `docs/access.md`, кухня и печать — `docs/kitchen.md`.

## 1. Почему не «облако с офлайн-очередью»

Ключевое наблюдение: **перебой интернета почти никогда не означает перебой
локальной сети**. У заведения падает канал наружу, а роутер, касса и кухонный
монитор продолжают друг друга видеть.

Архитектура, где терминалы общаются через облако, при таком обрыве ломается
в самом больном месте: официант отправил заказ, тот лёг в очередь на терминале,
и повар в трёх метрах его не получил. Никакая последующая синхронизация еду
уже не приготовит.

Поэтому источник истины переезжает **в заведение**.

## 2. Топология

```
┌─ Заведение ───────────────────────────────────────┐
│                                                   │
│   Касса (pos) ─┐                                  │
│   Касса (pos) ─┼─► Локальный узел ── PostgreSQL   │
│   Кухня (kds) ─┘        │                         │
│                         │                         │
└─────────────────────────┼─────────────────────────┘
                          │  синхронизация, когда есть связь
                          ▼
                     ┌─────────┐
                     │ Облако  │  отчётность, мультиточка,
                     │         │  тарифы, обновления
                     └─────────┘
```

**Локальный узел** — это отдельный мини-ПК либо одна из касс. Для шаурмечной
с единственным терминалом узел и есть эта касса: отдельной коробки не нужно,
меняется только роль процесса, а не архитектура.

Так же устроен iiko (`iikoRMS\Server` ставится в ресторане). Отличие нашей
схемы — облачный контур с тарифами и мультиточкой, которого у них нет:
это и есть продуктовое отличие, а не побочная деталь.

## 3. Три уровня деградации

| Уровень | Что случилось | Что работает                                                                                                                                                                                                                                                                    |
| -------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 0              | всё в порядке  | всё                                                                                                                                                                                                                                                                                     |
| 1              | нет интернета | **вся работа заведения**: заказы, кухня, наличные, фискальные чеки, смены. Не работает: оплата картой, мультиточка, обновления, свежая отчётность в облаке |
| 2              | умер узел         | терминал продолжает свою смену в одиночку: свои заказы, наличные, фискальный чек. Чужих столов не видит                                                                                               |

Уровень 1 — штатный режим, а не авария: заведение может так работать сутками,
и никто из персонала не должен этого замечать.

Уровень 2 — аварийный и ограниченный. Полноценную репликацию «каждый с каждым»
(как у iiko с `revision`/`lastModifyNode` и подсистемой обмена) мы намеренно
не строим: она стоит версионирования строк в каждой сущности, а закрывает
редкий случай смерти железа.

**Оплата картой офлайн невозможна в принципе** — эквайринговый терминал сам
ходит в банк. Это не наше ограничение, и обходить его нечем; касса обязана
внятно сказать кассиру «только наличные», а не показывать непонятную ошибку.

## 4. Что где живёт

| Данные                                              | Хозяин | Направление   |
| --------------------------------------------------------- | ------------ | ------------------------ |
| Заказы, позиции, платежи, смены  | узел     | узел → облако |
| Столы и расстановка                      | узел     | узел → облако |
| Станции, выводы, очередь печати | узел     | узел → облако |
| Меню, цены, техкарты                      | облако | облако → узел |
| Сотрудники, роли, PIN                       | облако | облако → узел |
| Тариф и квоты организации           | облако | облако → узел |
| Стоп-лист                                         | узел     | двусторонне   |

Правило: **оперативные данные рождаются в заведении, справочники приезжают
из облака**. Стоп-лист — единственное исключение: его ставит кухня локально,
но менеджер может снять его из облака.

## 5. Правила синхронизации

Разрешение конфликтов асимметрично по классам сущностей, и это не тонкая
настройка, а требование предметной области.

- **`orders`** — last-write-wins по времени изменения. Заказ это состояние,
  и последнее состояние верно.
- **`order_items`** — **append-only, всегда**. Позицию нельзя потерять при
  слиянии: потерянная позиция это либо несъеденное блюдо, либо неоплаченное.
  Отмена выражается статусом `voided`, а не удалением строки.
- **`payments`** — **append-only и иммутабельны**. Деньги нельзя
  перезаписывать: LWW на платеже означает потерянную выручку.
- **Фискальные документы** — иммутабельны по определению, только добавление.
- **Справочники** — односторонняя репликация облако → узел. Терминал их
  не меняет, конфликтов не бывает.

Идемпотентность обеспечивает `client_id`, который терминал присваивает
сущности при создании: повторная отправка не создаёт дубль.

## 6. Нумерация документов

Номер заказа в смене называют гостю на прилавке — он нужен **немедленно**
и не может ждать синхронизации. При этом два терминала не должны выдать
один номер.

Решение: узел выдаёт терминалу **блок номеров** при открытии смены (например,
сотню), терминал раздаёт из своего блока и запрашивает следующий, когда
подходит к концу. Блок выдан заранее — значит, номера продолжают выдаваться
и в офлайне, а пересечься не могут по построению.

Альтернатива «номер = префикс терминала + счётчик» отвергнута: гостю неудобно
слышать «заказ два-сорок семь», а персоналу — искать его в очереди.

## 7. Тариф в офлайне

Инвариант №1 («тариф проверяется на бэкенде, всегда») остаётся в силе,
но «бэкенд» теперь означает **локальный узел**.

Узел получает entitlements из облака и кеширует их со **сроком годности**:
пока он не истёк, узел принимает решения самостоятельно. Без этого обрыв
интернета выключал бы кассу целиком — то есть ровно то, ради чего вся
автономность и строится.

Срок годности должен переживать разумный простой связи (порядка недели)
и продлеваться при каждой успешной синхронизации. Просроченный кеш — повод
для предупреждения персоналу и последующей блокировки платных модулей,
но не базовой кассы: оставить заведение без возможности принять наличные
из-за проблем со связью недопустимо.

## 8. Что это значит для кода

**Фронт уже готов сильнее, чем кажется.** `apps/desktop` целиком работает
на локальном состоянии, печать марок идёт из Rust мимо сервера, права
проверяются локально. Переписывать экраны не придётся — localStorage
превращается из источника данных в кеш поверх узла.

**Меняется контракт бэкенда**, и это надо знать до того, как он написан:

- API узла и API облака — **разные**. Терминал ходит только в узел.
  Узел ходит в облако. Терминал в облако не ходит никогда.
- Realtime-события (инвариант №3) остаются внутри заведения: комнаты
  `venue_id` + `terminal.kind` живут на узле, и обрыв интернета их не касается.
- Облаку нужен приём пакетов синхронизации с идемпотентностью по `client_id`,
  а не CRUD-эндпоинты для терминалов.
- Схема БД узла и облака совпадает по оперативным таблицам — это позволяет
  лить данные как есть, без трансформации.

## 9. Что осознанно не делаем

- Репликацию «каждый с каждым» между терминалами (уровень 2 остаётся
  ограниченным).
- Разрешение конфликтов человеком: интерфейса «выберите правильную версию»
  не будет — правила из §5 должны покрывать все случаи автоматически.
- Работу кассы при просроченном кеше тарифа дольше разумного срока: это
  открытая дверь для бесплатного использования через отключение сети.
