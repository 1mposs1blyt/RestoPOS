# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Статус репозитория

Монорепо на pnpm workspaces, **шесть воркспейсов**: в `apps/` — два Tauri v2 +
React фронтенда (`desktop`, `mobile`), в `packages/` — три пакета.
`apps/backend` — **не воркспейс**: там лежит узел на C# со своей схемой БД,
и pnpm про него не знает.

**Сервер в репозитории есть — на C#** (`apps/backend/server`, ASP.NET Core
net8.0 + Dapper + Npgsql). Черновик на Fastify удалён
(коммит «удаление TS сервера»): узел пишется на C#, и держать
TypeScript-заглушку значило бы поддерживать код, который выбросят. Команды
`pnpm dev:backend` нет, узел собирается и запускается своим `dotnet`
(воркспейсом pnpm он не является). Каноническая схема — `apps/backend/server/Data/schema.sql`,
PostgreSQL, 39 таблиц, проверена на 16-й версии.

**Слушает он `http://localhost:5140`** (`Properties/launchSettings.json`,
профиль `http`; профиль `https` добавляет 7213). БД прописана строкой прямо
в `Program.cs`: `resto-db` на `127.0.0.1:5447`, пользователь `postgres`.
CORS открыт ровно на `localhost:1420` — порт dev-сервера кассы; поднимете фронт
на другом порту, и запросы будут отбиты браузером, а не узлом.

**Маршруты, которые у узла есть на самом деле** (сверяйся с исходниками
контроллеров, а не с `docs/plan.md`: план описывает целевой контракт, и с фактом
он уже расходился):

| Маршрут | Контроллер | Использует фронт |
|---|---|---|
| `POST /auth/pin`, `POST /auth/override` | `AuthController` | `data/session-source.ts` |
| `GET /session/bootstrap` | `SessionController` | `data/session-source.ts` |
| `GET /session` | `SessionController` | никто (фронт зовёт только `bootstrap`) |
| `GET /api/v1/venues/{id}/tables`, `PUT .../tables/{id}` | `HallController` | `data/tables-source.ts` |
| `GET /api/v1/venues/{id}/orders` | `HallController` | `data/occupancy-source.ts` |
| `GET /api/v1/venues/{id}/menu` | `MenuController` | `data/menu-source.ts` |

Пути к узлу собирает `NodeApi` (`packages/api-client`), и сверять его надо
именно с этой таблицей.

**Меню переехало на узел** (`data/menu-source.ts` + `state/menu.tsx`).
Проверено запросом к живому узлу 19 августа 2026: форма ответа совпадает
с `MenuSnapshot` до поля — `price` строкой (`"250.00"`), `isStopListed`
булевым, ключи в camelCase.

Две вещи, о которые спотыкаешься при отладке именно этого маршрута:

- **сид меню в БД сам не приезжает.** `Script0002_SeedMenu.sql` встроен
  в сборку ресурсом, но `DatabaseInitializer` неоткуда вызвать (см. «Схема БД»),
  так что `GET .../menu` на чистой базе честно отдаёт `{"categories":[],"items":[]}`.
  Накатывается он руками:
  `docker exec -i resto-db psql -U postgres -d resto-db < apps/backend/server/Data/Script0002_SeedMenu.sql`;
- **у всех позиций сида `prepStationId` — `null`**, потому что
  `menu_items.prep_station_id` он не заполняет вовсе. Для кассы это значит, что
  отправка на кухню считает такие позиции готовыми сразу (`stationId === null`
  → `isAutoReady` в редьюсере заказов), а марок не печатает ни одной. Симптом
  выглядит как поломка кухни, а это пустое поле в данных.

**Терминал ходит в узел, если задан `VITE_NODE_URL`** (`apps/desktop/.env.local`,
в git не попадает). Тогда сотрудник, его права и тариф приезжают **с узла**,
а демо-пины (1111/2222/3333/4444/9999) и матрица прав на фронте не участвуют
вовсе. Симптом «у роли пропало право, хотя в контракте оно есть» надо искать
в узле, а не в `packages/shared-types`.

### Код узла не править

**`apps/backend/server/**` — чужая зона. Читать можно и нужно, менять нельзя**,
даже когда правка на одну строку и баг очевиден. Узел ведёт бэкендер, и правка
с другой стороны приезжает ему конфликтом в файле, который он в этот момент
переписывает.

Что делать вместо этого:

- нашёл баг узла — **опиши его**: файл, строка, при каком условии срабатывает.
  Не чини;
- нужны данные — наполняй **БД** напрямую (`docker exec -i resto-db psql -U postgres
  -d resto-db ...`; снаружи контейнера она на `127.0.0.1:5447`), а не сидом внутри
  сервера. Данные не код;
- эндпоинта нет — фронт живёт на локальном состоянии дальше и ждёт, а не
  получает заглушку в узле.

Единственное исключение — `apps/backend/server/Contract.generated.cs`: он
генерируется из `contracts/contract.json` командой `pnpm contracts:build`
и руками не правится ни с какой стороны.

Запускать узел (`dotnet run --project apps/backend/server`) и собирать его
для проверки — можно: это не правка.

Линтер и тесты есть: Biome, Vitest, общий гейт `pnpm verify`. Плюс свои тесты
у Rust-части кассы (`src-tauri`, печать марок) — команда ниже.

**`pnpm verify` не трогает Rust вовсе.** Гейт остаётся зелёным при сломанном
`cargo test` и при не собирающемся релизе кассы — так уже случалось, и поломка
прожила несколько коммитов. Правя `src-tauri`, гоняй `cargo test --lib`
и `cargo check --release` руками; на зелёный `pnpm verify` тут полагаться нельзя.

`apps/desktop` — рабочая касса, **к узлу подключена частично**. Через него идут
вход по PIN с правами (`data/session-source.ts`), схема зала
(`data/tables-source.ts`), занятость столов (`data/occupancy-source.ts`) и
меню (`data/menu-source.ts`). Остальное — заказы, смены, оплата, кухня,
станции — по-прежнему на локальном состоянии, и маршрутов под них у узла нет.
Устройство описано ниже, в разделе «Фронтенд кассы». `apps/mobile` пока
остался одним экраном-заглушкой на `DEMO_ORDERS`.

**Каждый переезд на узел делается отдельным `data/*-source.ts`** по образцу
четырёх существующих: модуль знает про `isNodeConfigured()`, экраны и сторы —
нет. Так демо-режим остаётся рабочим, а появление эндпоинта не требует
править экраны.

**Заглушки под несуществующие эндпоинты не пишем.** Все четыре переезда
начинались с готового маршрута, и каждый потребовал подгонки под то, что узел
отдаёт на самом деле: `NodeApi` написан по `docs/plan.md` и разошёлся с фактом
уже трижды — префикс `/api/v1/venues/{id}`, построчное сохранение столов вместо
документа целиком и меню, у которого в плане не было ни заведения в пути,
ни отсутствующих модификаторов. Модуль, написанный до эндпоинта, не экономит
время, а даёт файл, который придётся переписать.

```bash
pnpm install
pnpm verify             # общий гейт: контракт + lint + typecheck + тесты + сборка
pnpm test               # vitest run
pnpm lint               # biome check .
pnpm typecheck:front    # tsc --noEmit по фронтам и пакетам
pnpm build:web          # vite build обоих фронтендов
pnpm dev:desktop        # tauri dev
pnpm --filter @restopos/desktop dev   # только фронтенд, без Tauri-обвязки
pnpm --filter @restopos/desktop tauri build   # .exe + установщики msi и nsis
```

Схема применяется напрямую, без обвязки:

```bash
psql -U postgres -v ON_ERROR_STOP=1 -f apps/backend/server/Data/schema.sql
```

Rust-часть кассы проверяется своими тестами (печать марок), `cargo` при этом
может не быть в PATH текущей оболочки:

```powershell
$env:PATH = "$env:USERPROFILE\.cargo\bin;$env:PATH"
cd apps/desktop/src-tauri; cargo test --lib
```

### Окружение этой машины

Этот раздел уже трижды устаревал — **сверяйся с фактом, а не с текстом**.
Проверено 19 августа 2026. На текущей машине:

- ОС — **Windows 11** (`win32`, x64). Оболочка — PowerShell; Bash тоже доступен,
  но синтаксис у них разный.
- `pnpm` **в PATH** (10.33.0), corepack не нужен. Node 22.22.0.
- **.NET SDK 10.0.302 в PATH**, при том что узел таргетит `net8.0`: собирается
  он новым SDK через targeting pack, отдельный SDK 8 ставить не нужно.
- **Rust установлен** (3 августа 2026, раньше его не было): `rustc`/`cargo` 1.97.1,
  тулчейн `stable-x86_64-pc-windows-msvc`; рядом VS 2022 Build Tools с C++ workload
  (`C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools`) и WebView2
  Runtime. Сборка кассы под Windows проверена целиком: с нуля ~3.5 мин
  (около 500 крейтов), инкрементально ~1 мин. Артефакты — в
  `apps/desktop/src-tauri/target/release/`: `desktop.exe`, `bundle/msi/*.msi`,
  `bundle/nsis/*-setup.exe`; всё это под gitignore, в репозиторий не попадает.
- **Кириллица в `productName` ломает MSI, но не NSIS.** WiX 3 линкует базу в
  кодовой странице локали, а дефолтная `en-US` — это 1252, где «Касса» непредставима:
  `light.exe` падает пачкой `LGHT0311`. Поэтому в `tauri.conf.json` задан
  `bundle.windows.wix.language: ["ru-RU"]` (кодовая страница 1251). Не убирай его
  и не «чини» переименованием продукта в латиницу. NSIS-установщик собирается
  независимо от этого — если MSI некстати сломается, `--bundles nsis` даёт
  рабочий инсталлятор.
- **Тип терминала в релизной сборке переключается сервисным экраном.** Вход
  под ролью `support` (демо-PIN `9999`) открывает `screens/servicescreen.tsx`:
  тип терминала, режим заведения, тариф, диагностика и сброс данных. Дев-панель
  внизу (`layout/AppShell.tsx`) осталась, но она под `import.meta.env.DEV`
  и в проде вырезается целиком.

  Обходной путь через инспектор ещё работает и остаётся на случай, когда экран
  недостижим (у крейта `tauri` для этого включена фича `devtools`, `Cargo.toml`):

  ```js
  localStorage.setItem('restopos.terminal.kind', '"kds"')      // кухня
  localStorage.setItem('restopos.venue.serviceMode', '"counter"') // прилавок
  location.reload()
  ```

  Значение — валидный JSON (кавычки внутри строки обязательны): `loadState`
  прогоняет его через `JSON.parse`. Перезагрузка нужна потому, что оба значения
  читаются один раз в инициализаторе `useState`.
- **Сборка держит файлы.** `vite build` чистит `dist/`, а cargo перезаписывает
  `target/release/desktop.exe` — оба падают (`EBUSY`, `os error 5`), если внутрь
  `dist/` зашёл какой-нибудь шелл или остался живой процесс `desktop.exe` после
  ручного запуска. Перед пересборкой: `Get-Process desktop | Stop-Process -Force`.

  **То же и с узлом, и промахнуться там легче.** `dotnet build` роняет
  `MSB3027`/`MSB3021` на копировании `apphost.exe` → `bin/Debug/net8.0/server.exe`,
  пока запущен сам `server.exe`, — а запущен он часто, потому что нужен кассе.
  Ошибка выглядит как поломка сборки, хотя компиляция прошла: чтобы **проверить
  код, не трогая чужой запущенный узел**, собирай в сторону —
  `dotnet build apps/backend/server/server.csproj -o <временный каталог>`.
  Так проверено 19 августа 2026: 0 ошибок, 0 предупреждений.
- **Переводы строк держатся `.gitattributes` (`eol=lf`).** Не убирай: генератор
  контракта пишет LF, а git под Windows отдавал файл с CRLF, и `pnpm
  contracts:check` падал на свежем клоне при совпадающем содержимом. Скрипт
  теперь сравнивает без учёта переводов строк, но чинить это нужно с обеих сторон.
- **В репозитории лежит `package-lock.json`, и это ловушка, а не второй способ
  установки.** Менеджер здесь один — pnpm, истина одна — `pnpm-lock.yaml`.
  npm-овый лок приехал вместе с C#-сервером и с тех пор дважды разъезжался
  с pnpm-овым в одном коммите (`npm install` где-то запустили, и он утащил
  за собой платформенные бинарники biome и rolldown). **Ставь только `pnpm
  install`**; увидел правку `package-lock.json` в диффе — это след чужого
  `npm install`, а не изменение зависимостей.
- **`apps/backend/server/obj/**` отслеживается git, хотя `obj/` есть
  в `.gitignore`.** Файлы попали в индекс до появления правила, а `.gitignore`
  на уже отслеживаемые не действует — поэтому артефакты сборки узла регулярно
  всплывают в диффах (`server.AssemblyInfo.cs`, кэши). В коммит их не тащи;
  вычищать индекс — это правка чужой зоны, договаривайся с бэкендером.
- Android SDK стоит (`ANDROID_HOME`), но `apps/mobile/src-tauri/gen/{android,apple}`
  не сгенерированы — их создаёт `tauri android init`. В Rust дело больше не упирается,
  но саму команду никто не запускал: понадобятся NDK и android-таргеты `rustup`.
- **iOS невозможен**: нужен macOS с Xcode.

Документация проекта ведётся на русском — придерживайся этого языка в README, комментариях
и сообщениях коммитов.

## Устройство монорепо

Пакеты `@restopos/{shared-types,api-client,ui-kit}` экспортируют **исходники**
(`exports` → `src/index.ts`), шага сборки у них нет. Из этого следуют две неочевидные
привязки, которые легко сломать:

- новый воркспейс-пакет надо добавить в `optimizeDeps.exclude` в `vite.config.ts`
  обоих приложений, иначе Vite пре-бандлит его и HMR перестаёт видеть правки;
- Tailwind v4 сканирует классы по путям из `@source` в `src/index.css`. Классы,
  добавленные в новый пакет вне `packages/ui-kit/src`, в CSS не попадут,
  пока туда не добавлена соответствующая строка `@source`.

Path-алиасы живут в `tsconfig.base.json`, от которого наследуются все проекты.

**`contracts/contract.json` — источник истины для прав, ролей, кодов ошибок,
имён realtime-событий и тарифной лестницы.** Он нейтрален по языку, потому что
узел пишется на C# и импортировать TypeScript не может. Отсюда порядок работы:

- правится **только** `contracts/contract.json`;
- `packages/shared-types/src/contract.generated.ts` и
  `apps/backend/server/Contract.generated.cs` — генерируемые файлы, руками
  не трогать: `pnpm contracts:build` пишет оба сразу;
- `pnpm contracts:check` встроен в `pnpm verify`, так что отставший
  сгенерированный файл роняет проверку;
- узел обязан спрашивать права через `Contract.PermissionsOf` /
  `Contract.CanApprove`, а не своим списком. Рукописная копия там уже была:
  у менеджера не оказалось `hall.layout.edit`, и конструктор зала исчезал
  с экрана ровно в тот момент, когда касса подключалась к узлу;
- `access.ts` держит только производные типы и хелперы. Тип `RolesMatchContract`
  в нём — компиляционная проверка, что `StaffRole` и роли контракта совпадают:
  разъедутся — перестанет собираться.

Дублировать матрицу прав руками в двух языках нельзя: разъедется на первой
правке, а расхождение здесь — это дыра в доступе.

**Тарифы в контракте есть, но пока только проверяются — не генерируются.**
Блок `planCodes` / `featureCodes` / `planFeatures` / `planQuotas` описывает
лестницу целиком, и `scripts/build-contract.mjs` гоняет по нему проверок больше,
чем по правам: коды пригодны для идентификатора (`multi-venue` с дефисом дал бы
синтаксически неверный TypeScript в чужом файле), каждый тариф описан в обоих
разделах, фичи существуют, квоты целые ≥ 1, и **лестница обязана расти** —
апгрейд, который что-то отбирает, роняет сборку. Причина строгости в том, что
ошибка тут либо отдаёт оплаченный модуль бесплатно, либо отбирает у клиента
оплаченное, и оба случая замечают не в тестах.

Но в `contract.generated.ts` и `Contract.generated.cs` этот блок **не попадает**,
и значения сейчас продублированы руками в трёх местах: `PlanCode` / `FeatureCode`
в `packages/shared-types/src/common.ts`, `PLAN_FEATURES` в
`apps/desktop/src/app/entitlements.tsx` и сид `plans` / `plan_features`
в `schema.sql`. На 19 августа 2026 все четыре копии сходятся — проверено.
Это ровно та ситуация, против которой написан абзац выше, просто про деньги
вместо доступа; правя лестницу, правь все копии сразу, а лучше доведи генератор
до конца, чтобы копий не осталось.

Порты dev-серверов разведены намеренно: desktop 1420, mobile 1430 (HMR 1431) —
чтобы обе кассы поднимались одновременно. Они продублированы в `devUrl`
внутри `src-tauri/tauri.conf.json`, менять надо в обоих местах.

### Фронтенд кассы (`apps/desktop`)

Каркас разложен по слоям, и порядок вложенности провайдеров в `App.tsx` значим:
`EntitlementsProvider` → `SessionProvider` → (сессия разблокирована) →
`AccessProvider` → `TablesProvider` → `OrdersProvider` → `NavigationProvider` →
`AppShell`. Тариф снаружи сессии, а не наоборот: он свойство организации и
существует независимо от того, кто за терминалом, а вход по PIN обязан знать
оплаченные модули — иначе он не может решить, есть ли сотруднику что делать
на этом терминале. Данные живут внутри открытой смены: блокировка терминала
размонтирует сторы, состояние переживает её в localStorage
(`src/lib/storage.ts`, префикс `restopos.`).

- **Разграничение доступа целиком описано в `docs/access.md`** — модель, матрица
  прав, две эталонные конфигурации (шаурмечная и ресторан) и контракт бэкенда.
  Ниже только то, что нужно, чтобы не сломать код.
- `src/app/navigation.tsx` — типизированный `Route` со стеком. Роутера-библиотеки
  нет намеренно: терминал работает в киоске, URL не виден и делиться им не с кем.
  `routesFor(scope)` кодирует инвариант №5: экран доступен, когда сходятся
  **четыре независимых условия** — тип терминала, режим обслуживания, право
  сотрудника и оплаченный модуль. Условия лежат таблицей `ROUTE_SPECS`,
  а не ветвлениями: входов уже четыре, и каждый следующий `switch` по типу
  терминала пришлось бы переписывать целиком.

  **Пометка `accessory` в `ROUTE_SPECS` — не косметика.** Так помечены экраны,
  которые доступны почти всегда и сами по себе не повод пускать сотрудника
  за терминал: главное меню, личная страница, оплата, экран заказа, журнал,
  табель, отчёты, стоп-лист, гости, документы. Без этой пометки пересечение
  прав никогда не оказалось бы пустым, и **отказ входа перестал бы срабатывать** —
  повар у кассы попадал бы внутрь и видел один экран со своей выработкой.
  Считать «есть ли тут работа» надо через `hasWorkOn(scope)` / `workRoutesFor(scope)`,
  а не через `routesFor(...).length`. Стартовый экран (`defaultRouteFor`) по той же
  причине возвращает `null`, когда рабочих экранов нет, даже если сопутствующие есть.
- `src/app/access.tsx` — `can()` для прав, которых просто нет, и `authorize()`
  для тех, что подтверждаются чужим PIN (`order.item.void`, `order.cancel`,
  `order.foreign`, `payment.refund`, `order.discount`). Правило: непобиваемое
  право гасит кнопку, побиваемое — ведёт в диалог. Матрица роль→права живёт
  в `packages/shared-types/src/access.ts`, одна на фронт и бэкенд; дублировать
  её в экранах нельзя, как и проверять роль вместо права.
- `src/app/entitlements.tsx` — `FeatureGate` и набор фич по тарифу. Это **UX**,
  а не защита (инвариант №1); дев-панель внизу экрана переключает тариф локально.
- `src/state/orders.tsx` — единственный источник правды по заказам, и касса, и KDS
  читают его. Инвариант №6 выражен статусом позиции: `new` — ещё не отправлена,
  её можно править и удалять; после отправки (`cooking`+) удаление запрещено.
  Открытие заказа и добавление позиции дедуплицируются **в редьюсере**, а не
  в вызывающем коде. Причина одна и та же: два вызова подряд видят один снимок
  состояния — эффект в StrictMode выполняется дважды, а по кнопке меню на
  сенсорном экране регулярно попадают двойным касанием. Снаружи повтор
  не отличить от первого раза, и позиция задваивалась двумя строками по одной
  штуке вместо «x2».
- `src/screens/tablescheme.tsx` — схема рисуется **1:1, без масштабирования**.
  Позиция стола хранится в долях холста (`cx`/`cy`, 0..1), размер — в пикселях.
  Абсолютные пиксели привязывали расстановку к разрешению терминала, где её
  рисовали (схема с 1920 на моноблоке 1024x768 частично уезжала за границы,
  и до тех столов нельзя было дотронуться). Промежуточный вариант с логической
  поверхностью 1600x900, вписываемой в экран, оказался хуже: её пропорции 16:9
  не совпадают с полосой зала (около 2.7:1), упиралась высота, и чем плотнее
  менеджер заполнял холст конструктора, тем сильнее всё сжималось при выходе.
  Доли решают перенос между терминалами без масштаба вообще, а холст
  конструктора совпадает с холстом просмотра — что разложил, то и видишь.
  Расстановку отдаёт `data/tables-source.ts`: с узлом — из его БД, без узла —
  из localStorage с миграцией трёх поколений формата.
- `src/state/tables.tsx` — геометрия расстановки. Статуса стола там нет: занятость
  вычисляется из активных заказов, иначе один факт хранился бы в двух местах.
  **Узел умеет только двигать столы** (`PUT .../tables/{id}` с геометрией):
  создания, удаления и переименования у него нет, поэтому в режиме узла эти
  кнопки экран не показывает вовсе. Дать менеджеру разложить зал и потерять
  его при обновлении — хуже, чем не показать кнопку.
- **Занятость столов — `state/occupancy.ts` + `data/occupancy-source.ts`.**
  Три вещи там неочевидны, и все три обязательны:
  - **запросов два, по одному на статус.** `GET /orders` без параметра
    возвращает у узла **все** заказы заведения, включая оплаченные: фильтра
    активных у него нет. Забрать всё и отсеять на клиенте — это история
    заведения за всю его жизнь на каждое обновление зала;
  - **сумму по столу с узла не показываем.** Он отдаёт `totalAmount`
    константой `0.00`, и «0 ₽» на занятом столе официант прочтёт как
    «ничего не заказано». Поле `total` в `TableOccupancy` для этого
    и сделано `null`-евым;
  - **занятость — объединение узла и локального стора**, а не выбор одного.
    Пока экран заказа локальный, а зал уже читает узел, оба говорят правду
    про разные заказы. Только узел — свободным выглядит стол, за которым
    сидят; только стор — теряются заказы других терминалов.

  Опрос раз в 10 секунд, а не подписка: realtime на узле пока нет вовсе.
  Ошибка опроса **не стирает** прошлые данные — зал, мигающий пустотой при
  секундном обрыве, хуже зала, отставшего на десять секунд.
- **Меню — `state/menu.tsx` + `data/menu-source.ts`.** Было модулем констант,
  стало стором по образцу `tables`: три состояния (грузится, готово,
  не доехало) и `reload`. Экраны, по которым заказывают, показывают разницу
  через `screens/menunotice.tsx` — **пустое меню и недоехавшее меню это
  разные сообщения**: в первом случае в заведении не завели блюд, во втором
  молчит узел, а кассир, увидевший пустой список, объяснит гостю, что всё
  распродано.

  Отсюда три следствия, которые и потребовали правок за пределами самого меню:

  - **категория выбирается лениво.** `MENU_CATEGORIES[0].id` в инициализаторе
    `useState` больше не существует: на первом рендере меню ещё едет. Экраны
    держат `pickedCategoryId: UUID | null` и падают на `categories[0]?.id`,
    так что первая категория выбирается сама, когда меню доехало;
  - **чистые функции получают меню параметром, а не импортом.** Редьюсер
    заказов (`stationOf` в действии `order/send`), отчёты (`findMenuItem`
    в `ReportContext`) и сборка строк чека (`receiptItems`) раньше тянули
    демо-каталог напрямую. Это тихо делало их зависимыми от константы:
    с узлом чек собрался бы по чужому меню, а тесты «проверяли» раскладку
    станций, лежащую в другом файле;
  - **локальный стоп-лист никуда не делся.** Узел отдаёт `isStopListed`
    флагом (`stop_list` с остатком ≤ 0), а `state/stoplist.tsx` хранит
    **остаток**: «осталось три порции» флагом не выражается, и экран заказа
    по-прежнему спрашивает его, а не поле из меню.
- **Режим обслуживания** (`Venue.serviceMode`) — `tables` или `counter`. У прилавочных
  заведений (шаурмечная, кофейня навынос) схемы зала не существует: вместо
  `hall`/`order` там единственный экран `counter`, заказ создаётся с `tableId: null`,
  и гостя зовут по `Order.number` — номеру в смене. Это не «урезанная касса»,
  а другой набор экранов над тем же API (инвариант №5), поэтому маршруты выдаёт
  `routesFor(kind, serviceMode)`, а не константа по типу терминала.
  На `counterscreen.tsx` три колонки: чек, меню и очередь заказов в работе —
  на прилавке кассир обычно сам и готовит, держать очередь в голове нельзя.
  Оплата там же отправляет на кухню: платят вперёд.
- Тикеты кухни считаются **от позиций**, а не от статуса заказа
  (`useOrders().kitchenTickets`). На прилавке платят вперёд, заказ сразу
  становится `paid` — но еда от этого не готова. Тикет уходит с экрана, когда
  позиции отданы, а не когда получены деньги. Ключ тикета — пара «заказ +
  станция»: один заказ разъезжается на кухню и бар отдельными тикетами.
- **Кухня описана в `docs/kitchen.md`.** Коротко: экран и принтер — это два
  **вывода одной станции**, а не два механизма; разведя их, получишь марку
  с тем, чего нет на экране. Станция без включённого экрана работает по бумаге,
  и её позиции становятся `ready` сразу при отправке — иначе двигать их статусы
  некому и тикеты копятся вечно. Отправка и печать — одна операция
  (`usePrinting().fireOrder`), звать `sendToKitchen` напрямую из экранов нельзя.
- Деньги — строки (`Money`), арифметика только через `src/lib/money.ts` в копейках.
- **Денежная логика вынесена в чистые функции под тестами**, а не размазана
  по экранам. Их пять, и каждая закрывает ошибку, которую иначе заметят
  при сверке кассы, а не сразу:
  `lib/payment-split.ts` — раскладка внесённого («внесено» и «сумма платежа»
  это разные величины: гость даёт 1000 за чек на 700, записать надо 700,
  иначе выручка завышена на сумму всех сдач за день);
  `lib/discount.ts` — скидки и надбавки (**надбавка не отрицательная скидка**,
  а свой род: иначе их не разделить в отчёте, а в сумме они дают ноль);
  `lib/cash-totals.ts` — свод смены (в ожидаемую наличность идут **только**
  наличные платежи, иначе недостача на размер безнала при каждом пересчёте);
  `lib/split-quantity.ts` — деление блюда (остаток отдаётся долям, чтобы
  три доли по 0.333 не потеряли копейку);
  `lib/receipt-lines.ts` — раскладка итога по строкам чека (скидка применяется
  к заказу целиком, а ККТ требует, чтобы сумма позиций сошлась с суммой
  платежей **до копейки**, иначе документ отклонён посреди расчёта гостя).
- **Смен три, и они независимы**: смена заведения (`shifts`, по ней номера
  заказов), кассовая смена ФР (`cash_shifts`, по ней номера чеков и Z-отчёт)
  и личная смена сотрудника (`staff_shifts`, табель и личные продажи). Личная
  открывается **кнопкой**, а не входом по PIN: за терминал подходят и между
  делом — подтвердить чужое сторно, глянуть отчёт, — и автооткрытие заводило бы
  явку, из которой потом считается зарплата. Отработанное время начинается там,
  где человек это подтвердил. Подробности — `state/shifts.tsx`.
- **Оплата — список строк** (`payOrder(orderId, drafts)`), а не один способ:
  часть картой, часть наличными. Тип оплаты — справочник (`data/payment-types.ts`),
  род и название копируются в платёж снимком, потому что закрытый чек это
  финансовый документ. Возврат — встречная строка с `refundOf`, не правка;
  проводится он через `state/checkout.tsx`, а не прямым вызовом стора: у него
  тот же нерушимый порядок с ККТ и эквайрингом, что и у продажи.

Общие компоненты живут в `packages/ui-kit` и переиспользуются обоими приложениями
(`PinPad`, `NumKeyboard`, `TextKeyboard`, `PinDots`, `AuthForm`, `OrderCard`,
бейджи статусов). `TextKeyboard` — полная ЙЦУКЕН/QWERTY с двумя раскладками:
имя гостя пишут по-русски, а внешний номер из агрегатора латиницей, и переключаться
приходится в одном поле.
Экран не должен верстать заново то, что уже есть в ui-kit. Пути к статике
(`/bg-logo.webp`) резолвит браузер от корня раздачи — `./public/...` не работает.

#### Набор экранов: четыре входа

Реализовано на фронте (`routesFor`), но заслона на узле за этим пока нет.
Контракт узел уже читает как положено — `Contract.PermissionsOf` в
`repos/AuthRepository.cs` выдаёт права роли, `Contract.CanApprove`
в `AuthController` подтверждает побиваемое право чужим PIN, — но это выдача
и подтверждение, а не защита эндпоинтов: **`requirePermission` не написан**,
и `HallController`, `MenuController`, `SessionController` отдают данные, не
спрашивая прав вовсе. См. «Контракт бэкенда» в `docs/access.md`. Прав
в контракте 40 на 5 ролей, и **все они на фронте пока UX, а не защита**
(инвариант №1).
Набор экранов определяют **четыре независимых входа**, и сводить их друг
к другу нельзя.

| Вход | Откуда | Что решает |
|---|---|---|
| `venue.serviceMode` | заведение, с сервера | есть ли зал физически: `hall`/`order` против `counter` |
| `terminal.kind` | регистрация терминала | касса, KDS или админка |
| `staff.role` | вход по PIN | что этому человеку можно из доступного на терминале |
| тариф организации | подписка | какие **модули** оплачены (`kds`, `warehouse`, `analytics`) |

Роль входит в набор через права (`permissionsOf(role)`), а не напрямую.
`CurrentScreen` пересчитывает `isAllowed` на каждом рендере и сбрасывает ставший
недоступным маршрут, так что смена сотрудника или конфигурации посреди смены
отрабатывает без отдельного кода. Пустое пересечение — это **отказ входа**
(`session.tsx`), а не пустой экран: повар у кассы должен понимать, почему
его не пустили.

Три ошибки, которые тут напрашиваются:

- **Режим обслуживания не выводится из тарифа.** Соблазн понятен: у шаурмечной
  и тариф минимальный, и зала нет. Но это совпадение, а не зависимость. Схема
  зала отсутствует потому, что еду выдают в руки, а не потому, что за неё
  не заплачено; апгрейд шаурмечной до Pro не должен внезапно подсовывать ей
  схему столов, а ресторану на Start зал нужен с первого дня. `serviceMode`
  приезжает с `venue`, тариф — с организации, и пересекаться они не должны.
- **Число сотрудников — это квота, а не фича** (инвариант №2). «Максимум 3
  человека» реализуется проверкой со счётом текущего использования
  (`max_staff`), а не булевым флагом в `plan_features` и уж точно не набором
  экранов. Тариф вообще не должен знать, сколько ролей совмещает один человек:
  если у него роль `manager`, он и получает экраны менеджера — независимо
  от того, что в заведении он один.
- **Роль на фронте — это UX, а не защита.** «Повару нельзя в зал» обязано
  подтверждаться на бэкенде (инвариант №1), иначе ограничение снимается прямым
  запросом к API мимо интерфейса. Роль и тариф проверяются независимо, обе
  проверки обязательны.
- **Роль `support` — не «менеджер с доступом ко всему».** У тех. специалиста
  ровно одно право `terminal.service`; ни заказов, ни денег он не видит.
  Инженер вендора с правом сторно в чужой кассе — это дыра, а не удобство.

### Целевое железо: сенсорный моноблок

Касса живёт на моноблоке с сенсорным экраном (Windows), типичные разрешения —
1024x768 и 1366x768, а не 1920. Отсюда правила, которые нельзя нарушать «по мелочи»:

- **Минимальная цель касания — 44px** (`min-h-11`), для часто нажимаемого —
  56px (`min-h-14`) и крупнее. Высоту задавай `min-h-*`, а не вертикальными
  `py-*`: паддинги легко обнуляются (см. ловушку со сбросом вне слоя), и кнопка
  молча схлопывается, а `min-height` переживает это.
- **Проверяй замером, а не на глаз.** `getBoundingClientRect()` по всем
  интерактивным элементам на 1024x768 и 1366x768; на глаз по скриншоту
  клавиатура в 140px вместо 288 не отличается от нормальной.
- Мышиных `hover` на терминале нет — состояние нажатия показывай `active:`.
- Указатель обрабатывай через Pointer Events (`onPointerDown` + `setPointerCapture`),
  а не `onMouseDown`: мышиные события пальцем не приходят, и перетаскивание
  на терминале просто не работает.
- Скроллбары внутренних списков стилизованы в `index.css` (узкие, тёмные):
  системная светлая полоса посреди тёмного экрана выглядит инородно, а пальцем
  в неё всё равно не попасть — списки листают смахиванием.

Три ловушки вёрстки, на которые уже наступали:

- **Сброс вне слоя убивает утилиты.** `@import "tailwindcss"` кладёт утилиты в
  `@layer utilities`, а объявления, написанные вне слоёв, выигрывают у любого
  слоя независимо от специфичности. Правило `* { margin: 0; padding: 0 }`
  в `index.css` обнуляло **все** `p-*`, `m-*` и `space-y-*` во всём приложении:
  `p-4` вычислялся в `0px`. Preflight Tailwind делает этот сброс сам — дублировать
  его не нужно. Если отступ «не применяется», сначала посмотри
  `getComputedStyle(el).padding`, а не подбирай классы.

- `cn` (`packages/ui-kit/src/cn.ts`) — простая конкатенация, **не** tailwind-merge.
  Базовый класс компонента и класс из пропа обе попадают в разметку, и конфликт
  решает порядок правил в CSS, а не порядок в строке. Не полагайся на то, что
  `className` «перебьёт» базовый: убирай конфликтующую утилиту из базы.
- `w-full` у компонента, который ставят во flex-колонку с `items-center`,
  резолвится против shrink-to-fit родителя и схлопывается до max-content
  содержимого. Задавай определённую ширину (`w-72`), а не `w-full`.

### Фискальный регистратор (`src-tauri/src/fiscal/`)

Слой ККТ живёт в Rust по той же причине, что и печать марок: драйвер —
нативная библиотека, из браузера её не вызвать, а регистрация чека обязана
иметь таймаут и восстановление после обрыва. Границы те же: фронт решает,
**что** пробивать, Rust — **как**.

- **Порядок нерушим: `эквайринг → фискальный чек → заказ оплачен`.** Чек
  до эквайринга — фискальный документ на платёж, которого может не случиться;
  заказ оплачен до чека — закрытый счёт без документа, то есть продажи
  с точки зрения налоговой не было.
- **Исходов регистрации три, а не два** (`RegistrationOutcome`). Третий —
  «неизвестно»: связь рвётся ровно тогда, когда чек уже в ФН, а ответ
  не доехал. Считать это ошибкой — пробить второй чек на те же деньги,
  считать успехом — потерять документ. Поэтому `register_with_recovery`
  идёт читать последний документ ФН и сравнивает `client_id` —
  **не сумму**: два заказа по 420 рублей подряд в фастфуде обычны.
  Не удалось и это — `NeedsAttention`, решает человек. Автоповтора здесь
  нет и быть не должно.
- **Реализация подменяется одной строкой — в `commands.rs::FiscalState::new`.**
  По умолчанию это `AtolDevice` по TCP/IP (`192.168.3.223:5555`): терминал стоит
  рядом с железом, и «касса молча пробила чек в эмулятор» — худший из исходов.
  Без ККТ под рукой эмулятор включается переменной окружения
  `RESTOPOS_KKT=emulator`. Второго места, где собирается устройство, быть
  не должно: оно уже было в `main.rs`, и подмена зависела от того, какой вход
  выполняется (см. «Два входа в крейт»). Порядок операций от модели ККТ
  не зависит и живёт в `mod.rs`.
- **Сценарии отказов** (`fiscal_simulate`) есть только в отладочной сборке —
  и сам эмуляторный API под `cfg`, включая `FiscalDevice::as_emulator`.
  Возможность сказать кассе «потеряй следующий ответ» в проде не должна
  существовать физически, а не быть спрятана за флагом.

  Отсюда же следует правило, о которое уже споткнулись: **регистрируется
  `fiscal_simulate` тоже только под `cfg`**. `generate_handler!` разворачивается
  на этапе компиляции и вырезанную функцию не переживает, поэтому список команд
  в `lib.rs` и задан дважды. Разница между списками ровно одна — два сценарных
  отказа; всё остальное обязано быть в обоих, иначе команда пропадёт из релиза.
- Деньги — целые копейки (`Kopecks`), округление половины вверх, как
  в `lib/money.ts`. Расхождение с фронтом на копейку в итоге чека недопустимо.
- Возврат копится **отдельной строкой** Z-отчёта, а не вычитается из выручки:
  «продали 0» и «продали 1000, вернули 1000» обязаны различаться.
- Просроченную смену (>24 ч) Z-отчёт закрывать **обязан**. Спотыкайся он
  о ту же проверку, что и чек, — касса, простоявшая ночь, не смогла бы
  ни пробить чек, ни закрыть смену.

#### Драйвер АТОЛ: пока это печать, а не фискализация

`fiscal/atol.rs` появился, и путать его с готовым ФР нельзя. **Из трейта
`FiscalDevice` у `AtolDevice` реализованы ровно два метода** —
`print_test_receipt` и `print_image`. `status`, `open_shift`, `close_shift`,
`x_report`, `register` и `last_receipt` там `todo!()`, то есть паникуют
при вызове. Проверено железом (АТОЛ по TCP/IP `192.168.3.223:5555`) именно
печатание: тестовая лента и логотип.

Отсюда два следствия, которые легко проглядеть:

- **касса с этим драйвером чек пробить не может.** `fiscal_register` уходит
  в `register_with_recovery` → `register` → `todo!()` → паника в потоке команды,
  а `commands.rs::lock` после неё отдаёт «драйвер ККТ в непригодном состоянии».
  Пока фискальные методы не написаны, расчёт гостя на этой сборке невозможен;
- **вызов драйвера идёт через PowerShell, а не через FFI.** `run_script`
  собирает скрипт, грузит `Atol.Drivers10.Fptr.dll` рефлексией
  (`C:\Program Files\ATOL\Drivers10\KKT\bin\`) и запускает `powershell
  -NoProfile -Command`. Обвязка (настройки связи, `open`, `finally` с `close`)
  одна на все операции намеренно: скопированная в каждый метод, она разъедется
  на первой правке, и симптом будет нелепый — тестовая печать идёт, картинка нет.
  Подставляемое в скрипт экранирует **вызывающий**: путь уезжает строкой
  в одинарных кавычках, у `canonicalize` под Windows снимается префикс `\\?\`,
  апостроф удваивается.

Печать картинки вынесена в команду `fiscal_print_image(path, scalePercent)`,
кнопка — на экране станций (`screens/stationsscreen.tsx`, карточка ККМ).
**Путь вводится руками, и это не временная небрежность**: файл читает драйвер
на машине терминала, поэтому браузерный `<input type="file">` дал бы объект
без пути, который драйверу не отдать; каталог раздачи фронта драйверу тоже
ничего не говорит. Логотипы под ленту лежат в `apps/desktop/public/`
(`receipt-logo-{384,576}.{png,bmp}`): два размера под ширину печати и два
формата на каждый. Какой из форматов ДТО берёт надёжнее — по коду не видно,
это выяснялось на железе; выбирая один, проверь оба.

#### Два входа в крейт: `main.rs` только зовёт `lib.rs`

Входов у крейта два — `main.rs::main()` и `lib.rs::run()`, — и это устройство
Tauri, а не дублирование. Правило одно: **`main.rs` не знает ничего, кроме
имени функции запуска**, вся сборка приложения живёт в `lib.rs::run()`.

Правило написано кровью. Своя `tauri::Builder` в `main.rs` уже существовала
(коммит «приколы всякие» перестал звать `desktop_lib::run()`), и списки команд
разъехались: в бинарнике не оказалось семи команд, которые фронт вызывает, —
печать марок, денежный ящик и весь эквайринг отвечали «команда не найдена».
Живая ККТ при этом была заведена в `main.rs`, а эмулятор — в `commands.rs`,
и какая из двух работает, зависело от того, какой вход выполняется.
Починено 19 августа 2026; проверено `cargo test --lib`, `cargo check --release`
и запуском отладочного бинарника.

Отсюда же то, что легко сломать снова: отладочная сборка (`cargo check`,
`pnpm dev:desktop`) переживает почти всё, чем эта поломка проявлялась. Правя
`src-tauri`, гоняй три проверки, а не одну:

| Что проверяется | Команда | Что ловит |
|---|---|---|
| тесты обоих слоёв | `cargo test --lib` | переименованные методы трейта, разъехавшиеся тесты |
| релиз | `cargo check --release` | `fiscal_simulate` в `generate_handler!` без `cfg` |
| набор команд | `grep invoke( apps/desktop/src` против списков в `lib.rs` | команду зарегистрировали в одном списке из двух |

Плагин `tauri_plugin_shell` `lib.rs` не поднимает, и это не упущение: драйвер
АТОЛ зовёт PowerShell сам, через `std::process::Command`, а фронту исполнение
команд не нужно. Разрешение `shell:allow-execute` в `capabilities/default.json`
осталось с прежней сборки и сейчас ни к чему не привязано — выдавать
из webview право запускать `powershell` с произвольными аргументами незачем,
эту строку стоит убрать.

### Эквайринг (`src-tauri/src/acquiring/`)

Устроен как слой ФР: трейт `PaymentTerminal`, эмулятор, сценарии отказов.
Протокол банка подключается в `AcquiringState::new`.

**Чем отличается от ФР — что делать на «не знаю».** У ККТ неизвестность
*читается*: спросили ФН последний документ, сверили `client_id`. Терминал же
общается с банком: пока исход неизвестен, деньги гостя уже могли уйти.
Поэтому там, где ФР перечитывает журнал, эквайринг **отменяет операцию
(reversal)**. Забыть про возможное списание — это деньги, снятые без чека,
которые потом ищут по банковской выписке за день. Отмена несуществующей
операции при этом безопасна и штатна: именно так её и шлют вслепую.

Оба Rust-слоя проверяются `cargo test --lib` (команда с путями к cargo выше).
Сценарии отказов взводятся из дев-панели (`layout/AppShell.tsx`) и существуют
только в отладочной сборке — в релизе их нет вместе с самой возможностью.
За трейтом `PaymentTerminal` по-прежнему стоит только эмулятор: протокола
банка нет, и на живой кассе слой этот ничего не спишет.

### Порядок расчёта (`state/checkout.tsx`)

**`эквайринг → фискальный чек → заказ оплачен`, и переставлять нельзя.**
Живёт в сторе, а не в экране оплаты: тот же порядок нужен прилавку, а
продублированная последовательность разъедется на первой правке.

Два правила компенсации, которые легко перепутать:

- **чек не состоялся → всё списанное возвращаем.** Две карты в одном чеке —
  обычное дело, и отказ второй не должен оставлять первую списанной;
- **исход регистрации чека неизвестен → НЕ отменяем.** Чек мог записаться,
  и отмена оставила бы фискальный документ без денег. Это `needsAttention`:
  ни повторять, ни закрывать заказ, решает человек.

Скидка применяется к заказу целиком, а ККТ требует, чтобы сумма позиций
сошлась с суммой платежей до копейки. Раскладку делает `lib/receipt-lines.ts`
(чистая функция под тестами), а строка чека несёт явную стоимость
(`line_total`, в ФФД это тег 1043) — цена за единицу со скидкой в целых
копейках просто не выражается.

Нефискальный режим включается, только когда ККМ **не заведена вовсе**
(браузерная отладка, терминал без ФР). Заведённая, но молчащая ККМ — это
блокировка оплаты, а не повод закрыть заказ без чека.

**Возврат идёт тем же порядком** (`checkout.refund`, экран `screens/refundscreen.tsx`):
деньги гостю → чек возврата прихода → встречные строки в заказе. Три вещи там
неочевидны:

- **возвращается чек целиком.** Частичный возврат — это не подмножество строк,
  а новый расчёт: ККТ требует, чтобы сумма позиций сошлась с суммой платежей,
  а скидка применена к заказу целиком. Частично возвращённый чек экран
  во второй раз не отдаёт;
- **что уже возвращено, решает `lib/refund.ts`** — чистая функция под тестами,
  и та же проверка стоит в `refundPayments`. Второе нажатие «Вернуть» отдаёт
  гостю сумму чека дважды, а замечают это при сверке кассы;
- **неизвестный исход возврата гасится отменой** (`refund_with_recovery`
  в Rust, зеркало оплаты): деньги, ушедшие гостю без встречной строки, ищут
  по выписке банка ровно так же, как списанные без чека.

**Возврат обязан вычитаться и в отчётах по позициям** (`lib/reports.ts`).
Отчёт по платежам (011) вычитает встречную строку сам, а выручка по официантам
(013) и реестр счетов (046) считаются от состава заказа — пропустив там возврат,
получаешь две правдоподобные и разные выручки за одну смену. Поправку вносит
`orderNet`, в одном месте, как и скидку. Расход блюд (023) возвращённый чек
исключает целиком: еда вернулась вместе с деньгами, а по этому отчёту заказывают
продукты.

### Оборудование (`state/devices.tsx`)

Один список на все устройства, как «Настройка оборудования» в iiko. Три вещи
оттуда влияют на расчёт:

- **Остановленное устройство отпускает COM-порт.** Порт держит ровно один
  процесс: пока касса запущена на нём, утилита производителя (ДТО Атол,
  тест Штрих-М) его не откроет, а она нужна для прошивки и фискализации.
  Поэтому `isRunning === false` — это режим обслуживания, а не поломка,
  и `state/checkout.tsx` блокирует оплату с отдельным текстом про запуск
  в настройках, а не с невнятным отказом драйвера.

  **Живая ККТ, на которой это отлаживается, подключена по TCP/IP**
  (`192.168.3.223:5555`, задано в `main.rs`), а не по COM — монопольного
  захвата порта там нет, и симптом «утилита АТОЛ не открывает кассу»
  на ней не воспроизведётся. Правило написано под COM-подключение,
  которое на моноблоках всё равно основное.
- **Денежный ящик — настройка ККМ, а не устройство.** Физически он на шлейфе
  чекового принтера и открывается его же командой; отдельного драйвера ящика
  не существует.
- **Система налогообложения и ставка НДС живут в карточке ККМ**
  (`taxSystem`, `defaultVat`). В `MenuItem` ставки нет вовсе, а фискальному
  чеку она обязательна; у общепита она обычно одна на заведение, и заводить
  её в каждое блюдо значит тысячу раз повторить одно и то же и однажды
  ошибиться в одном месте. Появятся блюда с разной ставкой (алкоголь на ОСН) —
  поле добавится в меню и будет перекрывать это значение.

### Схема БД (`apps/backend/server/Data/schema.sql`)

Схема — **источник истины для узла**, а не выгрузка из ORM: направление такое же,
как у контракта (`contract.json` канонический, TypeScript производный). Код узла
рядом уже лежит (`Controllers`, `repos`, `Services`), но пишется он от схемы,
а не наоборот, и Dapper тут выбран в том числе поэтому — миграции модели из кода
он не порождает.

PostgreSQL, 39 таблиц. Применяется напрямую через `psql`: **саму схему по-прежнему
никто не мигрирует**, таблица `schema_migrations` стоит пустая под будущий
инструмент.

Заготовка такого инструмента уже появилась, и её легко принять за работающую.
В зависимостях узла есть `dbup-postgresql`, а `Data/dbInit.cs` собирает
`DatabaseInitializer.Initialize`. Но:

- **вызывать его неоткуда** — `Program.cs` про него не знает, ни одной ссылки
  на `DatabaseInitializer` в коде нет;
- **`schema.sql` в сборку не встраивается.** Единственный `EmbeddedResource`
  в `server.csproj` — `Data/Script0002_SeedMenu.sql`, то есть DbUp накатил бы
  сид меню на уже существующие таблицы, а не схему;
- `EnsureDatabase.For.PostgresqlDatabase` там закомментирован, так что БД
  он тоже не создаст.

Иначе говоря, порядок пока ручной: `psql` со схемой, дальше данные.

**Разбор схемы iiko — `docs/iiko-reference.md`** (снимки в `docs/iiko/`).
Оттуда взята механика обмена, а не таблицы, и на это есть причина: у iiko
основного домена в схеме нет вовсе. Ни `Product`, ни `Employee`, ни `Table` —
всё лежит в одной таблице `entity` XML-блобом с дискриминатором `type`,
разбирать который умеет только их код. Отсюда же и ноль внешних ключей
на 192 таблицы. Скопировав это, мы получили бы данные, которые нельзя
ни запросить, ни проверить.

Что взято и зачем:

- `revision BIGINT` из общей последовательности плюс `deleted BOOLEAN` —
  обмен идёт «отдай всё, что больше ревизии N», а физически удалённая строка
  приедет обратно с другого узла, который про удаление не знает;
- `last_modify_node` — кто менял последним при мультимастере;
- `deleted_entities`, `replication_events`, `node_exchange_state` — надгробия,
  исходящая очередь и «докуда доехал каждый узел» (у iiko это `DeletedEntity`,
  `ReplicationEvent`, `TerminalExchangeState`);
- `inbound_staging` — приём пакетов из облака промежуточной таблицей: пакеты
  приезжают вперемешку, и строка может сослаться на ещё не приехавшего родителя.

**Ревизию проставляет база триггером `bump_revision`, а не приложение.**
Пропущенный `SET revision` в одном месте кода — это строка, которая никогда
не уедет в облако, и ловить такое по симптому «у одной кассы старая цена»
очень дорого.

Внешние ключи на узле есть и ловят ошибки рано: писатель там один и порядок
операций свой. Снимать их по всей схеме ради облака не нужно — для этого
и существует `inbound_staging`.

Расширяемость — два уровня, оба обязательны: `attributes JSONB` на ключевых
таблицах (произвольные поля без миграции, но с индексами и запросами, в отличие
от блоба) и реестр `custom_field_defs`, который описывает, что в этом JSONB
лежит. Без реестра JSONB превращается в свалку, где каждый интегратор кладёт
своё под своим именем.

Чего в схеме сознательно нет: ЕГАИС, бухгалтерия, накладные и производство,
EDI, лояльность. Это ~110 таблиц из 192 у iiko, и по дорожной карте они идут
позже — идём от клина вширь.

## Что это

Кассовая система для общепита (аналог iiko Front). Ключевая продуктовая идея: **один код,
одна сборка**, а объём функционала определяется тарифом организации на лету. Полное описание
архитектуры, схема БД и дорожная карта — в `README.md`; ниже только то, что определяет
принимаемые в коде решения.

**Как система работает целиком — `docs/workflow.md`**: смена от входа по PIN
до расчёта гостя, с явными пометками, что уже сделано, а что только решено.
**План работ и граница между фронтом и бэкендом — `docs/plan.md`** (он же ТЗ
для бэкендера: контракт узла, этапы, признаки готовности).
**Карта «экран → таблицы → операции» — `docs/routes.md`**: для каждого
маршрута сказано, что он читает, что пишет, какие эндпоинты и события ему нужны
и какие правила узел обязан соблюдать сам. Это то, с чего начинать бэкенд.

Разборы вглубь: `docs/access.md` (доступ), `docs/kitchen.md` (станции и печать),
`docs/autonomy.md` (работа без интернета), `docs/iiko-reference.md` (разбор iiko).

**Бэкенд не на Node.js: выбран C#**, и выбор уже воплощён — в репозитории лежит
работающий ASP.NET Core узел с четырьмя контроллерами, а не одна схема БД.
Черновик на Fastify удалён. Стек в `README.md` в этой части устарел.

Цель — полноценный конкурент iiko, включая автономную работу заведения при обрыве
связи (`docs/autonomy.md`). Догнать по ширине сразу нельзя: iiko развивают с 2005 года,
и одна только схема iikoRMS — 192 таблицы без фронта, доставки и лояльности. Поэтому
порядок работ идёт от клина (SaaS-касса для малого общепита дешевле iiko) вширь,
а не наоборот. Автономность при этом не «фича на потом», а фундамент: дописать
её задним числом нельзя.

Стек. Клиенты — React на Tauri v2 (не React Native) и на кассе/зале с KDS,
и в мобильном приложении официанта. База — PostgreSQL. Узел заведения —
**C# (ASP.NET Core net8.0 + Dapper + Npgsql), код в репозитории есть**.

`README.md` в части бэкенда **устарел**: там ещё описаны Node.js + Fastify,
Socket.io и BullMQ + Redis. Верь этому файлу и `apps/backend/server/Data/schema.sql`.

## Архитектурные инварианты

Это не рекомендации, а решения, из которых вытекает остальной дизайн. Нарушение любого
из них ломает модель продукта.

0. **Заведение работает без интернета.** Источник истины — БД **локального узла**
   в заведении (отдельный мини-ПК либо одна из касс), облако получает данные
   синхронизацией. Причина в `docs/autonomy.md`: перебой интернета почти никогда
   не означает перебой локальной сети, и касса с кухней в трёх метрах друг
   от друга обязаны продолжать работать. Оплата картой — единственное, что
   офлайн невозможно в принципе: эквайринговый терминал сам ходит в банк.
1. **Тариф проверяется на бэкенде, всегда.** `requireFeature('warehouse')` — middleware на
   каждом защищённом эндпоинте. `<FeatureGate feature="...">` во фронте — это UX (апсейл),
   а не защита: прямой запрос к API в обход UI должен получать отказ. «Бэкенд» здесь —
   локальный узел: он кеширует entitlements из облака со сроком годности, иначе
   обрыв связи выключал бы кассу целиком.
2. **Фичи и лимиты — разные механизмы.** Булевы модули живут в `plan_features`
   (`warehouse`, `egais`, `analytics`, …). Числовые ограничения (`max_terminals`,
   `max_venues`, число сотрудников) — это quota-проверки со счётом текущего использования,
   их нельзя реализовывать через feature-flag.
3. **WebSocket не переносит состояние.** Источник истины — только БД узла. События вида
   `entity.action` (`order.created`, `order_item.status_changed`, `table.status_changed`)
   лишь сигнализируют клиенту перезапросить данные. Класть полный заказ в payload события
   нельзя — это прямой путь к рассинхрону между залом и кухней. Realtime живёт внутри
   заведения, поэтому обрыв интернета его не касается.
4. **Изоляция комнат.** Подписка = `venue_id` + `terminal.kind` (`pos` | `kds` | `admin`).
   Кухня не должна получать события зала и наоборот.
5. **Все терминалы — тонкие клиенты локального узла.** Касса, KDS и админка различаются
   набором экранов и подписками, а не отдельными API или сборками. Терминал ходит только
   в узел, узел — в облако; терминал в облако не ходит никогда. API узла и API облака —
   разные: облаку нужен приём пакетов синхронизации, а не CRUD для терминалов.
6. **Разрешение конфликтов асимметрично по классам сущностей.** `orders` — last-write-wins
   (заказ это состояние). `order_items` — append-only: потерянная позиция это несъеденное
   либо неоплаченное блюдо, поэтому отмена выражается статусом `voided`, а не удалением.
   `payments` и фискальные документы — append-only и иммутабельны: LWW на платеже означает
   потерянную выручку. Справочники едут односторонне из облака. Идемпотентность даёт
   `client_id`, присваиваемый терминалом при создании. Подробности — `docs/autonomy.md`.

## Мультитенантность

Иерархия: `organizations` → `venues` → `terminals`/`tables`/`menu_*`, при этом `staff`
и `subscriptions` висят на организации, а не на заведении. Практически каждый запрос данных
должен быть ограничен по `venue_id` (а через него — по организации); отсутствие такого
фильтра — это утечка данных между арендаторами, а не просто баг выборки.

Аутентификация персонала на терминале — по PIN (`staff.pin_code_hash`), роли:
`waiter` | `cashier` | `manager` | `cook`. Роль (что человеку можно) и тариф (что оплачено
организацией) — независимые проверки, обе обязательны.

## Порядок реализации

Дорожная карта из README задаёт последовательность, и она не произвольная: биллинг
и feature-flags (v0.3) появляются **после** работающих модулей Start (v0.1) и Standard (v0.2).
Пока подписок нет, `requireFeature` всё равно должен стоять на эндпоинтах — иначе его
придётся дописывать задним числом по всему API.

Списание склада (`warehouse_items` через `menu_item_ingredients`) происходит в момент оплаты
и только при тарифе ≥ Standard.
